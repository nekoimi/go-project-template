# 插件化模块框架设计规划

> 状态：部分历史设计稿。模块 scope 已扩展为 HTTP、scheduler、worker；后台任务使用 Redis + Asynq，当前代码与 README 是最终依据。

当前项目已经具备 Gin、GORM、PostgreSQL、JWT、文件存储、WebSocket、定时任务等基础能力。随着模板能力增多，`internal/app/app.go` 和 `internal/transport/http/router.go` 会逐渐成为所有业务模块的集中耦合点。

本规划目标是把项目从“集中式应用模板”演进为“框架核心 + 可注册功能模块”的结构：框架只负责启动、基础设施和扩展点；外部功能模块像插件一样注册进框架。

### 设计目标

- **框架核心保持稳定**：配置、日志、数据库、路由基础、中间件、响应、错误码、定时任务、文件存储等能力由框架统一提供。
- **业务模块独立注册**：认证、用户、上传、WebSocket、指标、通知、权限等模块通过统一接口注册到框架。
- **新增模块少改核心代码**：添加功能时尽量只新增模块目录和注册入口，不在 `app.Initialize` 与 `SetupRouter` 中继续堆业务逻辑。
- **保持 Go 项目部署简单**：第一阶段采用编译期模块注册，不使用 Go 原生动态 `plugin.so`。
- **不引入 DI 容器**：坚持 Go 风格的显式构造函数注入，模块内部手动组装 repository、service、handler，不做自动装配。
- **可逐步演进**：先做模块注册机制，再逐步支持模块配置、生命周期、健康检查、定时任务、事件、队列等扩展点。

### 推荐架构

第一阶段采用“模块化单体 / 编译期插件”架构：

这里的“插件化”不是运行时安装插件，也不是动态加载 `.so` 文件，而是：

```text
模块像插件一样注册到框架，最终仍然编译为一个服务二进制。
```

这种方式保留插件化的扩展边界，同时符合 Go 项目偏显式、偏简单、偏静态编译的习惯。

```text
cmd/
  server/
    main.go
  scheduler/
    main.go

internal/
  app/                         # 框架启动器，负责组装基础设施和注册模块
  framework/                   # 模块接口、注册器、模块上下文、生命周期扩展点
  config/                      # 全局配置
  middleware/                  # 通用中间件
  pkg/                         # 通用工具包
  scheduler/                   # 定时任务引擎
  storage/                     # 文件存储抽象和驱动
  websocket/                   # WebSocket 基础能力

  modules/                     # 内置功能模块，后续业务优先放这里
    auth/
      module.go
      handler.go
      service.go
      repository.go
      dto.go
    user/
      module.go
      handler.go
      service.go
      repository.go
      dto.go
    upload/
      module.go
      handler.go
      service.go
    ws/
      module.go
```

第一阶段可以先保留现有 `handler/v1`、`service`、`repository` 目录，只新增 `module.go` 作为包装层，避免一次性大搬迁。

当前实现已经进入第二阶段：auth、user、upload 的 handler 和 service 已经收拢到各自模块目录；认证和用户 DTO 已分别放在对应模块中；auth 与 user 共同依赖的 `User` 持久化实体位于 `internal/domain/user`，仓储实现暂时保留在共享的 `internal/repository` 层。

### 核心模块接口

建议在 `internal/framework` 中定义最小接口：

```go
type Module interface {
	Name() string
	Register(ctx *ModuleContext) error
}
```

模块通过 `Register` 完成自己的依赖构建和能力注册，例如路由、定时任务、健康检查等。

### 模块上下文

框架通过 `ModuleContext` 向模块提供基础设施：

```go
type ModuleContext struct {
	Config    *config.Config
	Logger    *zap.Logger
	DB        *gorm.DB
	Router    *gin.Engine
	API       *gin.RouterGroup
	Protected *gin.RouterGroup
	Scheduler *scheduler.Scheduler
	Storage   storage.FileStorage
	WSManager *ws.Manager
	Health    *HealthRegistry
}
```

上下文只暴露稳定能力，不暴露具体业务模块对象，避免模块之间直接耦合。

### 模块注册示例

认证模块可以这样注册：

```go
type Module struct{}

func NewModule() *Module {
	return &Module{}
}

func (m *Module) Name() string {
	return "auth"
}

func (m *Module) Register(ctx *framework.ModuleContext) error {
	userRepo := repository.NewUserRepository(ctx.DB)
	authService := NewService(
		userRepo,
		ctx.DB,
		ctx.Config.JWT.Secret,
		time.Duration(ctx.Config.JWT.ExpireHours)*time.Hour,
	)
	authHandler := NewHandler(authService, ctx.Logger)

	auth := ctx.API.Group("/auth")
	auth.POST("/register", resp.Handle(authHandler.Register, ctx.Logger))
	auth.POST("/login", resp.Handle(authHandler.Login, ctx.Logger))

	return nil
}
```

用户模块可以注册到受保护路由：

```go
func (m *Module) Register(ctx *framework.ModuleContext) error {
	userRepo := repository.NewUserRepository(ctx.DB)
	userService := NewService(userRepo)
	userHandler := NewHandler(userService, ctx.Logger)

	users := ctx.Protected.Group("/users")
	users.GET("/profile", resp.Handle(userHandler.GetProfile, ctx.Logger))

	return nil
}
```

这样 `httptransport.SetupRouter` 不再需要接收具体的 `AuthHandler`、`UserHandler`、`UploadHandler`。

### 注册方式

第一阶段推荐显式注册：

```go
modules := []framework.Module{
	auth.NewModule(),
	user.NewModule(),
	upload.NewModule(),
	ws.NewModule(),
}

for _, mod := range modules {
	if err := mod.Register(moduleCtx); err != nil {
		return nil, nil, fmt.Errorf("register module %s: %w", mod.Name(), err)
	}
}
```

显式注册的优点是清晰、可控、容易排查问题，适合作为项目模板的默认方式。

后续如果需要更强的插件感，可以增加 registry：

```go
framework.Register(auth.NewModule())
framework.Register(user.NewModule())
framework.Register(upload.NewModule())
```

再配合空导入：

```go
import _ "github.com/example/project/internal/modules/auth"
```

但不建议第一阶段就依赖 `init()` 自动注册，避免启动顺序和调试复杂度上升。

### 路由职责调整

当前 `internal/transport/http/router.go` 负责基础路由，业务路由由各模块自行注册：

```go
func NewBaseRouter(cfg *config.Config, logger *zap.Logger, db *gorm.DB) *RouterContext
```

`RouterContext` 包含：

```go
type RouterContext struct {
	Engine    *gin.Engine
	API       *gin.RouterGroup
	Protected *gin.RouterGroup
}
```

基础路由继续由框架注册：

- `GET /health`
- `GET /ready`
- `GET /swagger/*any`
- 静态上传目录 `/uploads`
- 全局中间件
- JWT 保护组

业务路由交给模块注册：

- `/v1/auth/*`
- `/v1/users/*`
- `/v1/upload/*`
- `/ws/v1/chat`

### 配置设计

第一阶段可以增加简单模块开关：

```yaml
modules:
  auth:
    enabled: true
  user:
    enabled: true
  upload:
    enabled: true
  websocket:
    enabled: true
```

框架提供辅助方法：

```go
func (ctx *ModuleContext) ModuleEnabled(name string) bool
```

模块注册时自行判断：

```go
if !ctx.ModuleEnabled("auth") {
	return nil
}
```

后续可以扩展为模块独立配置：

```yaml
modules:
  notification:
    enabled: true
    provider: smtp
    queue: true
```

### 定时任务扩展

当前定时任务集中注册在 `internal/scheduler/registry.go`。模块化后，任务应该由模块自行注册：

```go
func (m *Module) Register(ctx *framework.ModuleContext) error {
	if ctx.Scheduler == nil {
		return nil
	}

	_, err := ctx.Scheduler.AddJob("0 */5 * * * *", jobs.NewExampleJob(ctx.Logger))
	return err
}
```

也可以封装：

```go
ctx.AddCronJob("0 */5 * * * *", jobs.NewExampleJob(ctx.Logger))
```

这样通知模块、清理模块、统计模块都能各自维护自己的任务。

### 生命周期扩展

第一阶段只保留 `Register`。当前第三阶段已经增加生命周期接口，用于 worker、队列消费者、外部连接、长连接管理等场景：

```go
type Bootable interface {
	Boot(ctx context.Context, moduleCtx *framework.ModuleContext) error
}

type Shutdownable interface {
	Shutdown(ctx context.Context, moduleCtx *framework.ModuleContext) error
}
```

例如 WebSocket 模块可以在 `Boot` 中启动 manager，在 `Shutdown` 中关闭所有连接。未实现这些接口的模块会被自动跳过，保持显式、轻量。

启动流程：

```text
加载配置
初始化基础设施
创建基础路由
注册模块
执行 Boot 钩子
启动 HTTP 服务
优雅关闭时执行 Shutdown 钩子
释放数据库、日志等资源
```

### 健康检查扩展

当前第三阶段已经支持模块注册健康检查：

```go
ctx.AddHealthCheck("database", func(ctx context.Context) error {
	sqlDB, err := db.DB()
	if err != nil {
		return err
	}
	return sqlDB.PingContext(ctx)
})
```

框架统一聚合到 `/ready`：

```json
{
  "status": "ready",
  "checks": {
    "database": "ok",
    "redis": "ok",
    "minio": "ok"
  }
}
```

这样 Redis、MinIO、队列、第三方服务都可以由模块自行暴露检查逻辑。

### 事件扩展

如果模块之间需要通信，不建议直接互相引用 service。可以后续引入轻量事件总线：

```go
type EventBus interface {
	Publish(ctx context.Context, event Event) error
	Subscribe(topic string, handler EventHandler)
}
```

示例：

- 用户注册成功后发布 `user.registered`
- 通知模块监听后发送欢迎邮件
- 审计模块监听后写审计日志

这样模块之间通过事件解耦。

### 依赖注入策略

第一阶段继续使用手动构造依赖，明确不引入 `wire`、`dig`、`fx` 或类似 DI 容器：

- 当前项目规模适合手动 NewXXX，清晰直接。
- 模块内部自己组装 repository、service、handler。
- 框架只向模块提供基础设施，不替模块管理所有业务对象。
- 依赖关系直接体现在代码里，便于阅读、调试、测试和重构。
- 初始化错误尽量停留在编译期或显式返回值中，不通过容器延迟到运行期暴露。

在 Go 项目中，依赖注入更推荐理解为“通过构造函数显式传入依赖”，而不是“使用容器自动注入依赖”。

推荐写法：

```go
func (m *Module) Register(ctx *framework.ModuleContext) error {
	repo := repository.NewUserRepository(ctx.DB)
	svc := NewService(repo)
	h := NewHandler(svc, ctx.Logger)

	users := ctx.Protected.Group("/users")
	users.GET("/profile", resp.Handle(h.GetProfile, ctx.Logger))

	return nil
}
```

不推荐写法：

```go
container.Provide(repository.NewUserRepository)
container.Provide(NewService)
container.Provide(NewHandler)
container.Invoke(registerUserRoutes)
```

后续即使项目变大，也优先通过拆分模块、整理构造函数、增加小型 builder/factory 来降低初始化复杂度，而不是默认引入 DI 框架。

### 边界原则

- 框架不能依赖具体业务模块。
- 模块可以依赖框架提供的稳定接口。
- 模块之间不要直接互相 new 对方的 service。
- 跨模块协作优先通过接口、事件或框架注册能力。
- 公共能力放框架，业务规则放模块。
- 模块注册失败时，应用启动应该失败并输出明确模块名。

### 与 Go 原生动态插件的区别

Go 提供 `plugin` 包，可以加载 `.so` 动态库，但不建议作为当前阶段方案：

- Windows 支持不友好。
- 构建和部署复杂。
- Go 版本、依赖版本、构建参数必须严格一致。
- 调试和测试成本高。
- 对当前模板项目收益不大。

因此本项目优先采用“编译期插件化”：

- 模块像插件一样注册。
- 代码仍然一起编译。
- 部署仍然是一个二进制文件或一个 Docker 镜像。
- 依赖通过显式构造传入，不依赖自动注入容器。
- 后续如果真的需要动态扩展，再考虑进程外插件、RPC 插件或独立微服务。

### 分阶段落地计划

#### 第一阶段：建立模块注册骨架

1. 新增 `internal/framework`。
2. 定义 `Module`、`ModuleContext`、`Registry`。
3. 调整 `httptransport.SetupRouter`，只保留基础路由和基础分组。
4. 调整 `app.Initialize`，初始化基础设施后循环注册模块。
5. 将 auth、user、upload、websocket 包装为模块。

#### 第二阶段：业务按模块聚合

1. 新增 `internal/modules/auth`、`internal/modules/user`、`internal/modules/upload`。
2. 把对应 handler、service 迁移到模块内部。
3. `repository` 和 `model` 先作为共享层保留，避免 auth/user 之间产生不自然的包依赖。
4. 保留通用 response、error、middleware 在框架层。
5. 清理 `app.Initialize` 中的业务依赖构造逻辑。

#### 第三阶段：扩展点增强

1. 支持模块开关配置。
2. 支持模块注册定时任务。
3. 支持模块注册健康检查。
4. 支持生命周期 `Boot` / `Shutdown`。
5. 支持事件总线，用于模块间解耦通信。

当前实现状态：模块开关、定时任务注册、健康检查聚合、生命周期 `Boot` / `Shutdown` 已完成；事件总线待后续按实际模块协作需求再引入。

#### 第四阶段：外部模块化

1. 支持业务项目在框架外部定义模块。
2. 支持显式注册外部模块。
3. 根据需要支持 registry + 空导入注册。
4. 评估是否需要独立插件进程或 RPC 插件。

### 最终效果

框架启动流程会从“手动写死所有业务对象”变为：

```go
ctx := framework.NewModuleContext(...)

modules := []framework.Module{
	auth.NewModule(),
	user.NewModule(),
	upload.NewModule(),
	ws.NewModule(),
}

if err := framework.RegisterModules(ctx, modules...); err != nil {
	return nil, nil, err
}
```

新增业务模块时，只需要：

1. 创建模块目录。
2. 实现 `Module` 接口。
3. 在启动入口显式加入模块列表。
4. 如果需要，补充模块配置。

这样项目会保留模板的简单性，同时具备更清晰的扩展边界。
